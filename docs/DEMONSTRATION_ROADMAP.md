# Revised development roadmap — complete demonstration before institutional operations

Strategic clarification recorded 2026-10-27. The immediate project objective is a fully functional, production-representative **demonstration** using synthetic cases, fictional identities and appropriately licensed demonstration models/images. Institutional NGO/government operational approval processes begin after the complete demonstration is ready. They do not block development and testing of synthetic reporting, matching demonstrations, investigation UX, security or collaboration.

This roadmap proposes future work; **it authorizes no additional implementation phase, model download or dataset acquisition**. Current authorized outputs are the unchanged Phase 2C documentation draft PR and the proposed Phase 2D specification. [Phase 2D scope](phase2d/IMPLEMENTATION_SPEC.md), [contracts/data plan](phase2d/PROPOSED_CONTRACTS_AND_DATA.md) and [pending tests](phase2d/PROPOSED_TEST_MATRIX.md) remain proposals requiring explicit owner approval.

## Boundaries and terminology

- Synthetic engineering readiness means software behavior demonstrated with controlled fixtures; it does not establish child identification accuracy, demographic safety, identity or custody authority.
- A working facial recognition demonstration must actually execute a separately cleared detector/alignment/recognition pipeline on licensed fictional-face images and produce reproducible compatible embeddings/ranks. Existing geometric pixel grids and scripted leads do not satisfy that milestone and must not be relabeled as facial recognition.
- A licensed demonstration artifact is not a child-evaluation-qualified or operationally approved model. Exact code, weight, detector, aligner, export and image/generator rights must cover the proposed demo. Record provenance/restrictions and resolve applicable rights uncertainty before acquisition. Demonstration status is not a waiver for uncleared models or datasets.
- Actual longitudinal-child biometric validation needs a separately authorized dataset and protocol. A multi-photo demonstration with fictional chronology can be built first and cannot prove real aging robustness.
- Institutional operating approval, real child-data authority and production biometric activation remain later explicit gates. No real missing-child records, actual child photographs, public child search, automatic identity confirmation, custody disclosure or release is enabled by a demonstration.

The existing eight model profiles remain blocked under their current manifests. No candidate or image collection is newly cleared here. An appropriately licensed candidate may receive a new, separately reviewed demonstration-only artifact decision after evidence is resolved and the owner authorizes that work. Do not flip an existing blocked flag, reuse a wrapper's code license as a weight grant or fetch a model merely to investigate its license.

## Feasible artifact routes to investigate, not approved selections

Evaluate two bounded alternatives after separate authorization. One is a pretrained recognizer/detector with exact purpose-compatible weight/component rights and a wholly fictional licensed image set or generator. The other is an independently owned demonstration recognizer trained only from a documented rights-cleared fictional rendering pipeline; it still needs a detector/alignment contract, safe runtime, reproducible inference and honest limited capability. Neither route may borrow restricted weights, scraped real identities or an uncleared training corpus.

Check the exact training/provenance and restriction evidence required for the chosen scope; legal ambiguity means defer that artifact and choose another route, not defer all synthetic feature development. If a public publisher declaration is insufficient, resolve it or select an independently controlled asset. Third-party image copyright permission alone does not establish biometric processing authority for a real depicted person. Default demonstration inputs are fully fictional; real people are not silently treated as synthetic because names were changed.

Acquisition remains fail-closed, hash-verified and quarantined; no automatic model packs, hub/custom-code loading, untrusted pickle, public inference API or silent provider fallback. Rights-cleared assets and inference packages receive exact locked identities only when selected and compatibility-tested. This document installs or pins no speculative inference version.

## Functional milestone detail

DEMO-02 must show actual image-to-detection-to-alignment-to-embedding-to-ranked-case execution, with exact artifact/preprocessing/space IDs, reproducibility and nonfinite/wrong-space/unknown-image denials. Show explicit no-face/multi-face/quality failures. Test genuine known fictional subjects and deliberately absent fictional subjects, but label measured rates as synthetic demo behavior. Never transfer an upstream score or similarity into a probability of child identity.

DEMO-03 must preserve multiple images individually, rather than overwrite a single case age/date. Freeze deterministic photo caps and case aggregation before scores, report omitted/duplicate photographs and calibrate each synthetic photo-count arm separately. Include wide fictional chronology gaps, unknown/cross-bin intervals and contradictory claims; no hard age exclusion or face-estimated birthdate. Any fictional age render is marked generated and retains generator/source lineage. Age progression using actual subjects or a new generative model is a separately controlled proposal and is not authorized by this roadmap.

DEMO-04 implements the proposed synthetic workflow first. An eventual demo-only neural provider must be an explicit later integration change preserving the same access/evidence boundaries; it does not unlock existing operational matching APIs or convert the research/qualification lab into an operational case database. Staff always make investigative decisions; even two reviewers cannot turn a synthetic score into identity/custody authority.

## Complete stakeholder demonstration definition

The release candidate must run actual services, not a slide deck, stubbed backend or pre-rendered video:

1. A fictional missing report and fictional found report enter separate real intake flows with multiple licensed synthetic images and uncertain metadata.
2. Real quarantine/scanning/storage workers produce private sanitized derivatives; a malicious/mismatched fixture remains quarantined and an outage fails safely.
3. A synthetic NGO moderator reviews claims and grants a preauthorized fictional caseworker scoped access. Real MFA/session expiry, CSRF and database/RLS remain enabled.
4. The separately cleared demonstration recognition pipeline processes only approved fictional-face fixtures and ranks private opposite-registry candidates. A scripted result can explain a workflow fallback but cannot substitute for this recognition milestone.
5. A caseworker compares permitted evidence, per-photo chronology, provenance, missingness and limitations, rejects a false lead, holds insufficient evidence and escalates another fictional lead.
6. An already authorized colleague collaborates; distinct-person independent review and audit work. Same-person approval, wrong-tenant access, revoked grants and stale evidence fail.
7. A reporter/claimant cannot see candidate existence, photos, location or staff tasks. Public child search, automated identity and custody disclosure/release remain demonstrably disabled.
8. The same complete journey works in Arabic and English, keyboard/RTL/narrow layouts; fixtures reset reproducibly and restore does not revive revoked workflow access.

The demo is production-representative in its implemented service boundaries, authorization, evidence integrity and failure behavior. It remains isolated with fictional data and approved demonstration artifacts, visibly labeled, access-controlled, and unsuitable for real case operations. No deployment to a production child-data environment or unrestricted public image upload is implied.

## Regression and demonstration release gates

Retain official TesterArmy/e2e 0.21.3 with web engine 0.15.3 and locked Playwright dependency 1.64.1. Preserve all Chromium/Firefox/WebKit × Arabic/English × four-width targets, deterministic assertions, zero mandatory skips, disabled optional telemetry and no external testing model. Retain every existing API, real PostgreSQL/RLS, migrations, security/adversarial, identity, worker, integration, backup/restore and regression test. Add exact tests for every implemented feature; planned Phase 2D browser expansion is additional coverage, never a replacement.

Each milestone needs exact committed-head CI, actual required-check status, sanitized source/fixture/artifact hashes, actual passed/failed/skipped/missing counts, coverage and original failure evidence. Any critical security/safeguarding failure blocks completion. No synthetic pass establishes child biometrics or substitutes for independent model/privacy/penetration review. Licensed-model inference/parity and fictional-data retrieval tests stay separate from workflow/browser tests and from any future authorized real dataset evaluation.

Before stakeholder release, rehearse positive and failure scenarios, complete manual Arabic/English/accessibility review, record achieved reference-machine resource limits, verify private access and outbound-network restrictions, and provide a clear limitation statement. Institutions may then review a functional demonstration; any next real-data or operational proposal still needs separate explicit approval. Stop now at the specification and roadmap; no milestone implementation begins in this task.
