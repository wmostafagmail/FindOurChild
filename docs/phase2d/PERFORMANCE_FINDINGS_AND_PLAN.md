Reference observation: Linux x86_64 hosted runners report four logical CPUs and approximately 16 GiB RAM. Each actual TLS/Next BFF/Keycloak/API measurement uses 20 separately MFA-authenticated staff sessions, 100 query fixtures, 50 candidates/query, 100 queue and 100 comparison requests. Both final-head runs completed all 200 measured requests successfully. Setup, authentication and worker fixture publication are outside endpoint timing; normal endpoint authentication/authorization, database and audit work are inside it. No inference is measured.

Direct database measurements use 100 queries with 50 visible candidates and 20 real RLS sessions. They time a different access path and result size from the paginated API. They are not API latency and cannot be subtracted from the API measurements as a component estimate. Each run reports 100 samples per measured category; p95 is the sorted 95th observation, not a pooled population estimate. Full numeric samples-of-percentiles and hardware records are in [PERFORMANCE_REPEATABILITY.json](PERFORMANCE_REPEATABILITY.json). Raw per-request latency arrays and component timings were not retained by the original harness.

Repeatability result: queue and database targets were missed in **two of four** independent runs with identical code/configuration. Comparison met its target in all four. Queue p95 ranges 759.19–1,092.75 ms; database p95 906.98–1,198.38 ms. The final push overruns are 9.28% and 19.26% respectively. This establishes repeatable budget risk, not its frequency in production or a statistically stable service-level estimate. Four runs and 100 samples/category/run cannot establish a production capacity guarantee or a false-positive identification rate.

## Investigation and limits

Source inspection confirms that reads perform live identity validation, paired case/purpose checks, immutable migration-ledger validation, durable organization audit persistence and fresh post-audit authorization. Queue projection is repeated after the real audit wait. Direct-table RLS and the specialized queue projection have different workloads. Earlier forward migrations 0034/0035 and bounded, request-isolated IdP connection reuse improved previous local measurements; the present residual misses are still real observations.

Candidate explanations are CPU/database pressure, repeated policy/scenario work, organization audit-lock contention, IdP/pool wait, or hosted-runner variability. The available aggregate percentiles contain no component timings, CPU steal/IO-pressure series or matched query plans; **none of these is established as the sole root cause**. The fact that database and queue misses co-occur supports investigation, not a causal attribution to a shared host. Existing faster 16-CPU arm64 local measurements are a different environment and do not close the four-CPU hosted gap.

## Proposed corrective sequence

1. Freeze an execution-source manifest, fixture cardinalities/ages, images/container digests, database version, worker state and test order. Repeat at least five independent, serial envelopes on each declared reference environment; include clean-start and warmed-state series separately. Record CPU quota/steal, memory, IO, software versions and co-running services. The proposed roadmap's eight-core reference is a separate comparison, not permission to discard the observed four-core misses. Preserve every run and error; report distributions per run instead of pooling p95 values. Use the updated PR/push runs as additional independent observations, never overwrite earlier misses.
2. Add a separately reviewed diagnostic plan for numeric timing buckets: BFF/TLS, IdP request/pool wait, connection/transaction acquisition, initial projection, audit lock/persistence, post-audit projection and serialization. Keep tokens, case IDs, narrative, media, vectors and SQL parameter values out of published diagnostics. Instrumentation is proposed, not implemented by this remediation.
3. Profile the exact queries on synthetic copies under the real API/worker roles using bounded `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` and query/wait statistics. Compare cold/warm plans and the direct-table versus specialized queue paths. Do not use admin/bypass-RLS results as runtime performance evidence. Preserve paired permission, revocation, expiry, schema-ledger and evidence-snapshot semantics.
4. If plans justify it, propose forward-only indexes or statement-scoped redundant-work reductions. Never edit applied migrations 0001–0036, cache authorization/token results across requests, defer required audit persistence, remove post-audit checks, weaken independent approval, or change the workload/browser matrix to obtain a pass. Any audit-lock redesign requires an explicit integrity/concurrency review before implementation.
5. After an approved correction, rerun all affected unit/API/real PostgreSQL/RLS/security/recovery/adversarial tests and the complete official TesterArmy Chromium/Firefox/WebKit regression. Preserve old red/budget-miss evidence. Proposed performance closure: five of five independent declared-reference runs meet unchanged queue <=1,000 ms and comparison <=1,500 ms p95, with the separately declared database target and zero unsuccessful measured requests. Agree the reference/protocol and closure criterion in review; these are not silently activated new CI gates.

No performance correction, new profiling implementation or Phase 2E work is started here. Owner review must decide the remediation plan and any explicit carry-forward of the open performance gap. Functional acceptance, performance-budget attainment, scientific biometric accuracy and operational authorization remain separate claims.
