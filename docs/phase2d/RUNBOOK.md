# Synthetic investigation demonstration runbook

Use an isolated local clone and existing exact locks. No model/image-dataset acquisition is needed or authorized. Never copy operational credentials, case databases, photographs or private research datasets into it.

1. Install the pinned Python/Node tools, run `uv sync --locked` and `npm ci --ignore-scripts`.
2. Run `.venv/bin/python -m scripts.dev init`, then `db` and `api`. These commands provision the synthetic database, migrations, private storage, ClamAV and Keycloak realm; secrets stay in ignored `.runtime` files.
3. Run `.venv/bin/python -m scripts.workflow_validate`. It provisions closed procedural cases/media through the real scanner, executes the exact required unit/PostgreSQL lane, and restores the actual bounded worker. Fixture grants expire; they are not operational NGO approval or guardian verification.
4. Build and run the web service using existing scripts. Staff enter `/en/investigation` or `/ar/investigation` using privately provisioned synthetic MFA accounts. Credential values must never enter reports, screenshots, commits or model calls.
5. Start a sealed scenario, open a candidate, inspect each authorized photograph and its independent chronology, and record structured human decisions. A separately authorized synthetic safeguarding person must complete the independent stage. Assignment never grants access; rejected evidence cannot be recycled into an identity conclusion.

Local browser TLS trust is an environment prerequisite, not a reason to bypass certificate verification. The owner selected hosted TLS validation; the required GitHub workflow configures trust only on disposable hosted runners and executes all Chromium/Firefox/WebKit targets. No further macOS keychain changes are part of this phase.

Full regression: hosted workflow `phase1a-required`, plus the separately reported local scripts. `workflow_test synthetic_workflow_http` requires the actual TLS BFF/Keycloak/API/worker. Tests use real services and synthetic fixtures. Private operator fault tools are CLI-only, enforce synthetic database identity and a closed account/action list, and always restore injected revocation/audit faults. They are not application endpoints or staff privileges.

Recovery uses a quarantined fresh restore, a new independent private activation epoch, then explicit current permission/revocation reconciliation before any controlled synthetic reissue. Do not restore an old backup over the running database and reuse activation/session configuration. The native drill verifies backup/schema/RLS preservation and default denial in the restored copy. It does not certify production erasure or automate institutional activation.

Rollback: stop synthetic entry/worker leases, retain applied migrations and immutable evidence, and use an explicitly compatible binary or quarantined restore. Do not drop the new journal or rewrite 0001–0024. Current schema changes do not enable the generic biometric, custody or release APIs. Phase 2E requires separate acceptance and authorization.

The host live-HTTP fault runner creates a bounded, read-only, credential-free SQL relay from the existing worker image onto the existing internal network plus the application edge network needed for Docker Desktop loopback ingress. It connects only to `db:5432` and contacts no external endpoint. Its host listener binds only `127.0.0.1:55439`, verifies the synthetic database before execution and is removed in `finally`. The application database service itself publishes no port. Do not run overlapping service-lifecycle test lanes: worker stop/start, private storage recovery, lease/OOM and revocation fixtures require serial ownership. The OOM test uses only its own disposable 384 MiB container and removes it afterward; it does not exhaust the host or kill unrelated processes.

Readiness requires the actual authorized object after storage restart, not merely its listening port. Migration-ledger corruption and revocation injections restore the exact original values in `finally`. Never treat an environment failure, canceled run or partial artifact as a passing test. Apply new migrations forward without rewriting previously applied SQL.

Investigation history starts with a bounded 25-event page. Use **More history** until the current first-review event is visible before completing independent review. The server requires that exact current review ID and snapshot; an older loaded review cannot approve a newer conclusion. If collaboration changes the revision while paging, reopen the investigation and review the current history. Automated API tests cover multi-page history and stale/actor-bound cursors; a long-journal browser usability review remains a separate manual limitation.

Sign out remains available while a command is pending. Evidence clears immediately; completed sign-out state waits for the actual server response. If revocation cannot be confirmed, evidence remains hidden and the interface offers **Retry sign out**. Do not treat that failure state as confirmed server revocation. For a mutation whose response was lost, reopen the immutable history before retrying. Test-only logout faults target a single closed synthetic principal and the `session.logout` audit action, and are removed in `finally`; they are not application privileges.

Application and provider sign-out are distinct. After confirmed application sign-out, `/identity/me` denies the old session. To switch staff in the same browser, use **End provider session to switch staff** on the identity page, confirm on Keycloak's existing logout form, return to the identity page, and complete the other person's password and MFA. The fixed link targets only this synthetic environment's configured issuer and client; it carries no token, session hint or redirect parameter. Keycloak retains its own logout confirmation/CSRF protection. Browser tests and the live-HTTP independent-review test exercise this entire handoff without deleting cookies or bypassing MFA.

The full live-HTTP lane includes the actual metadata load measurement:20 separately MFA-authenticated synthetic staff sessions,100 query fixtures and50 candidates/run,100 queue and100 comparison requests. The real running worker publishes the fixtures. Setup, authentication and fixture generation are excluded from measured endpoint latency and reported as such; the endpoint timings include normal BFF, authorization, database and audit work. Temporary cases/grants/scenarios and owned clients are cleaned afterward. This run must not overlap a worker lifecycle lane. A missed planning latency target remains a reported gap; successful functional responses do not convert it into a met target.

Extending the job budget does not alter per-request bounds, test assertions, retries, target counts or failure blocking. Timed-out/canceled runs remain nonpassing. Actual API metadata latency targets remain separately measured planning budgets, not assertions of production capacity.
