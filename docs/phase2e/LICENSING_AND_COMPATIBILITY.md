## Training provenance and permissions still unresolved

The model README attributes encoder training to approximately three million faces from FaceScrub, VGG and scraped web images; the CNN detector combines images from several public datasets, and the five-point aligner uses author-collected web images/annotations. These descriptions are useful provenance disclosures, not complete subject authority, consent, removal history, demographic composition or longitudinal-child validation. No training corpus is acquired. The publisher weight dedication is a documented demo-use basis, not a warranty that all underlying privacy/publicity/training claims are resolved. Do not promote it to operational clearance.

The proposed media are publisher-described synthetic/CGI illustrations generated/refined using Qwen tools. The prior generator-card/license evidence is preserved, including the standalone Qwen-Image-Edit-license evidence limitation. Generators and their entire upstream training sets are outside this phase; no generator is downloaded/executed. The dataset includes classifier-derived demographic/caption analysis. Those predictions and excluded metadata are neither imported nor treated as truth. Its selected stylized, correlated views are not a representative child cohort and provide no actual aging intervals. A source's intended headshot linkage still needs independent human fictional-consistency review before using it as a demonstration correspondence label. Review must be blinded to recognition scores; report all fixed-pair failures.

If new contradictory terms, broken linkage, real-person material, unsafe content or a rights complaint appears, quarantine/revoke that artifact and its descendants. Do not silently replace it, scrape another source, contact subjects or claim no third-party rights risk exists. Seek owner review of a separately licensed alternative while unrelated synthetic workflows remain available. The restricted 68-point/iBUG models, convenience `face_recognition_models` bundle, other wrappers/backends and all eight blocked Phase 2B profiles remain excluded.

## Source-level technical findings

The pinned [recognition example](https://github.com/davisking/dlib/blob/2e0b3846b4dcd0953951a9c0172503c666975229/python_examples/face_recognition.py) and [binding](https://github.com/davisking/dlib/blob/2e0b3846b4dcd0953951a9c0172503c666975229/tools/python/src/face_recognition.cpp) specify a 150×150 RGB chip, padding 0.25 and a 128-component network output. The binding converts network float descriptors to double; `num_jitters<=1` uses its direct network path. Explicit-chip and image/landmark paths must be measured for parity, with storage dtype/tolerance recorded. No code here establishes runtime determinism across BLAS/compiler/hardware or actual model acceptance by the parser.

The five-point model's documented detector compatibility supports the planned pairing; native L2 distances remain native, without inherited cosine thresholds or automatic unit normalization. Existing future provenance v1 requires `unit_l2`, so an additive v2 model contract is necessary. Existing fixture media validators also intentionally reject these new media until a separately audited importer/provider is implemented. Equal vector dimension cannot overcome these compatibility differences.

The [CNN example](https://github.com/davisking/dlib/blob/2e0b3846b4dcd0953951a9c0172503c666975229/python_examples/cnn_face_detector.py) warns that it is computationally heavier and intended for GPU-speed use. CPU execution is a proposed baseline, not a speed guarantee. The [Python CMake source](https://github.com/davisking/dlib/blob/2e0b3846b4dcd0953951a9c0172503c666975229/tools/python/CMakeLists.txt) declares minimum CMake 3.10 and vendored pybind11; that minimum does not select a safe exact toolchain or certify current Python compatibility. [setup.py](https://github.com/davisking/dlib/blob/2e0b3846b4dcd0953951a9c0172503c666975229/setup.py) delegates to CMake. Do not execute example installation commands as the approved production build recipe. The CNN example also points at upstream `examples/faces` photographs; a full source archive would include unapproved media. E0 must use an explicitly reviewed data-free code/license projection, never assume code licensing clears example photographs.

Current API Python 3.13.13, native compiler/NumPy/ABI, codecs, CPU instructions, thread controls, safe load behavior, startup/RSS/latency and actual fixture detectability remain **untested for this model**. E0 must first produce a separate exact worker dependency lock, compiled-image digest, SBOM/license/security report and source-only ABI/API compatibility proof (A1b) **before weight/image acquisition**; actual load/inference/parity evidence follows the approved byte-integrity and safe-execution gates. No native package was installed by this revalidation. CPU/GPU/arm64 alternatives need their own review; no silent provider or preprocessing substitution is allowed.
