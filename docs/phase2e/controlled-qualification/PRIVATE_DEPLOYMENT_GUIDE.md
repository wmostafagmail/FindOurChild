## Hold, expiry and recovery

`... run --rm admin hold` is a root deny-only action: external-first epoch advancement, disable authority and permanently revoke all current local sessions. A restored older database cannot revive sessions with prior external epochs. Real IdP account/session revocation must also deny each subsequent operation through live introspection. A database outage, unknown key, expired 30-day binding/pin, stale MFA or failed proof must deny; no cached positive fallback exists.

Before restore, stop private API/worker and hold the deployment. Preserve the external checkpoint volume independently of the PostgreSQL backup, plus the immutable registry, root provisioning files, audit and fixture-exposure history. Restore into an isolated database first. Keep authority disabled. Never replace the external journal with a snapshot from the restored database. Compare DB exposure history against permanent external freeze records. After resolving mismatches, perform new actual owner MFA and a new local setup code, then `... run --rm admin recover`; it advances epochs, invalidates earlier sessions/producer epochs and journals the action. Lost external records or history mismatch require investigation, not automatic rebootstrap. Proof-use tombstones cannot be undone by SQL restoration.

A whole-host rollback or compromise of trusted root/runtime/checkpoint storage is outside the local journal's tamper-evidence guarantee. An independent protected backup/monotonic retention service and disaster-recovery operator procedure remain deployment requirements; generated CI does not establish their availability. The API's checkpoint access is the existing V3 trusted service boundary. Host/IdP/owner trust concentration remains disclosed.
