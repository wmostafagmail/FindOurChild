## Human roles and combinations

The project owner remains the actual owner; no owner signing key/principal is enrolled. Technical and fixture reviewers are **unappointed**. Role names below are policy categories, not invented identities. Owner designation must identify actual people and bind their personally controlled public keys and scope.

| Combination | Proposed decision and constraints |
|---|---|
| Owner + acquisition/build operator | Permitted. The owner can run the bounded tools and sign final execution, but cannot be their own technical or fixture approver for that execution chain. |
| Technical verifier + fixture reviewer | Permitted only by explicit dual designation, with separate role attestations. Complete and seal A6 before access to any recognition scores/ranks. A5 loading-only diagnostics must not contain image inference. |
| Owner + technical verifier, or owner + fixture reviewer | Not permitted on the same batch/execution chain. Prevents one person authorizing both the supporting review and final activation. |
| Technical verifier + acquisition/build operator | Not permitted for the evidence batch/build they approve. Separate scripts do not turn one human into two people. |
| Fixture reviewer + acquisition operator | Permitted only if that person is not also the technical approver for that batch, the48-image selection was frozen beforehand and they remain score-blind. All combined-role restrictions apply together. |
| All roles in one person; shared/private-key delegation | Not permitted. Different accounts or keys for the same person do not satisfy person-level separation. |
| Implementation author + verifier | Not automatically an independent review. Authorship/conflicts must be declared; the A1b waiver covers lack of independent security review, not missing technical evidence or the operator/final-owner separation above. |

Recommended minimum: **two actual humans** — owner/operator and a distinct technical/fixture reviewer, if dual designation and blinding are valid. This avoids an external-consultancy requirement while retaining a second person. It does not assert that either person has been appointed or that two people provide an independent security certification. Loss of a required role blocks progress; no assistant, service identity or newly generated default key substitutes for a human approver. Automated tools may collect evidence under a declared operator, but cannot sign a human review or silently appoint that operator.

Any image, link, label, split or gallery change requires the new blinded-review path above. Later knowledge of scores cannot be used to alter the sealed judgment or erase failures.

## Signed-record and deployment boundaries

Propose a new domain `FOC-PHASE2E-DEMO-APPROVAL-V2`, separate from current v1 permits and any operational namespace. Do not feed this proposal to the existing verifier or reinterpret a v1 signature as a v2 permit. Future implementation must use closed schemas and bounded canonical bytes, reject unknown/duplicate fields and unsafe numbers, and bind record kind, policy digest, project, principal/role/key, gate, exact manifests/build/input scope, deployment/registry/revocation epoch, unique record ID, issue/not-before/expiry and decision. Signature domain separation must cover record kind as well as payload; signing a nonce/enrollment cannot sign an inference permit.

Use Ed25519 verification rather than a custom cryptographic primitive. Public keys and signature formats must be validated with a reviewed library; format/canonicalization cross-language tests are required before the new policy is executable. Existing `approval.py` validates a different closed v1 format with <=24h lifetime and reviewer/operator separation; it remains unchanged and denies untrusted keys. This proposal implements neither a verifier nor a trusted registry.

Proposed maximum key enrollment:90 days, bounded by owner designation; A3/A4/A6 permits:24h; A5 load-only permit:30min; A7 execution permit:4h, no longer than any prerequisite/key. All durations are **proposed limits**, not issued approvals. Renewal requires fresh current-state checks; no silently extended signature. UTC clock uncertainty, stale registry/epoch or missing audit persistence fails closed.

Approver signatures authorize a specific action only after technical checks succeed. The private controlled provisioner—not a browser—must install approved fixed identities, policy and build pins. Every acquisition/read/unpack/scan/load/job publication checks live authority, deployment and artifact lineage. Inference remains offline; a trusted supervisor delivers bounded current authority, fences jobs, and denies publication if it cannot reconcile revocation. No generic path/URL/model loader, shared operational credential, public dataset route or service-generated human signature is introduced.

Future actual-inference CI must run on a controlled, reviewed exact source with private read-only artifact access; untrusted/fork jobs receive no asset-store credentials. Never use `pull_request_target` to execute untrusted code with those credentials. Human signing keys are never CI secrets. Missing approved assets or authority must block the required inference gate, not produce a green skip. Published reports remain sanitized/input-free; no model/image bodies, chips, raw vectors or private permits appear in public artifacts. This checkpoint configures none of those CI capabilities.
