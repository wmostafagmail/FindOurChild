# DEMO-ONLY trusted public-key enrollment — proposed procedure

**Design only; nothing is enrolled or issued.** No person has been designated by this packet. The assistant has generated no approver keys, challenge signatures, permits or default trusted identities. This procedure applies only if the owner approves the [demo amendment](DEMO_APPROVAL_POLICY_PROPOSAL.md) and separately authorizes implementation and enrollment.

## Key ownership and representation

Each actual human approver generates and retains their own Ed25519 private key locally, using an appropriately reviewed cryptographic tool and protected storage. They never send a private key, seed, passphrase or recovery material to the assistant, repository, CI, browser, chat or another approver. Backups remain under that human's control. No CI/service auto-signer may impersonate them.

Transfer only the public key and its fingerprint through the approved enrollment channel. Proposal: accept canonical Ed25519 SubjectPublicKeyInfo DER (PEM is only a transport wrapper), validate the Ed25519 algorithm and key encoding, then fingerprint the exact DER with SHA-256. Store any required raw-key conversion explicitly; a raw32-byte hash and a DER hash are different identities and must not be interchanged. Reject another algorithm, unknown/duplicate/trailing structures or the same public key assigned to different people. Ed25519 and its encodings are specified by [RFC8032](https://www.rfc-editor.org/rfc/rfc8032) and [RFC8410](https://www.rfc-editor.org/rfc/rfc8410). This packet supplies **no example real key or fabricated fingerprint**.

Separate role attestations must identify the same actual human when they hold multiple allowed roles. Multiple keys/accounts must never hide person-level conflicts. The owner designates competence/scope; a valid signature proves control of a key, not that a person inspected evidence, is qualified, or has independent judgment.

## Bootstrap and enrollment sequence

1. **Owner approves the policy design.** Record the exact approved policy digest and owner decision through the established authenticated project channel. The current instruction authorizes design only. Never treat this unsigned proposal as that approval.
2. **Establish the owner trust anchor out of band.** The actual owner locally generates their key and supplies its public fingerprint through an authenticated owner channel already established independently of that candidate key. A controlled administrator verifies owner identity/fingerprint through that channel and records the authorized bootstrap. A self-signed candidate key or Git push is not sufficient proof of ownership/authority. No trust-on-first-use browser endpoint or auto-import is permitted. Owner/admin bootstrap is an explicit governance trust assumption, not cryptographically independent proof.
3. **Prove possession without granting authority.** A future enrollment tool creates a single-use random challenge bound to enrollment record ID, exact public-key fingerprint, project, approved policy, actual principal, requested roles and short challenge expiry. The human signs it locally. Verify the signature/domain and consume the challenge exactly once. This is proof of possession only; it cannot authorize an artifact, enrollment or execution. No challenge is generated by this design packet.
4. **Owner designates technical and fixture reviewers.** Resolve actual person identities and conflicts before registration. Record permitted roles, instance/project scope, validity interval, contact/recovery channel and the owner's designation. Owner signs each exact enrollment record after possession/identity checks. The recommended two-person arrangement and forbidden combinations are in the policy. Do not assign placeholders as people.
5. **Controlled provisioning and readback.** After separate authorization, a trusted private provisioner verifies the bootstrap/owner signature and policy, writes a versioned registry atomically with least privilege, then independently reads back key fingerprints, roles, validity, scope and monotonic registry epoch. Browser/API/workers cannot write it or supply their own registry path/trust root. Log only minimized enrollment references; no private material. Copies in Git, documentation or a test fixture are not trusted enrollment.
6. **Dry-run negative validation before use.** In a separate test namespace, verify unknown/revoked/wrong-role/expired keys, cross-deployment/policy replay, conflicting person roles and invalid signatures all deny. Synthetic unit keys stay test-only and cannot enter the enrolled demo registry. None of this is claimed executed here.
7. **Keep activation disabled.** Only after approved policy, actual enrolled keys and all prerequisite technical evidence may a later authorized acquisition permit be considered. Enrollment alone permits no download, unpacking, decode, model parse or inference. Final A7 requires the actual owner's signature over the complete reviewed chain.

## Proposed registry and signed-record fields

The future private registry must bind version/domain, project and isolated deployment, approved policy digest, registry/revocation epoch, actual principal ID and person linkage, key ID/canonical DER/fingerprint/algorithm, allowed roles/gates, not-before/expiry, owner enrollment authorization, possession evidence, status and revocation reason/effective time. Root/public-key rotation and delegation changes are separate signed records, never editable history. No actual values are populated in this proposal.

Each future gate record must bind the above authority plus its unique record ID, action, exact predecessor/evidence/asset/build/space digests and time limits. Artifacts and paths are fixed by the reviewed manifest; a signature cannot extend an allowlist. Future schema/canonicalization/library choices need implementation review and negative tests. Preserve the existing v1 verifier and production/qualification gates; a new demo namespace must reject cross-policy signatures in both directions.

## Expiry, revocation, rotation and recovery

- Proposed enrollment validity is <=90 days; permits remain within the stricter per-gate lifetimes in the matrix and never outlive a prerequisite. Use a trusted UTC clock and monotonic deadlines for execution; uncertainty/stale state denies. Expiration requires new owner authorization, not an edited timestamp.
- Owner revokes any delegated key/role. An approver reports compromise through the authenticated emergency channel; the controlled operator pauses affected actions immediately while ownership is reconciled. A pause grants no new privilege. Revocation is irreversible for that key and advances the independently maintained epoch. Re-enrollment uses a new human-generated key and fresh designation/possession checks.
- Every dependent permit is revalidated against current revocations, including queued/running jobs and result/media reads. Invalid authority suspends derived evidence, fences publication and triggers required cleanup/review; it does not silently retroactively bless previously signed material. Artifact permission withdrawal is a separate tombstone, not erased by signing-key rotation.
- Offline workers cannot assume a registry copy is current indefinitely. A trusted supervisor must issue short-lived, action-specific authority and enforce cancellation/resource deadlines; the server must recheck current epochs before publication. If current state cannot be established, fail closed. This supervisor/registry integration is **not implemented** by this packet.
- Normal owner-root rotation requires the old enrolled owner key, a separately authenticated owner fingerprint confirmation, new-key possession proof and an explicit registry update. If the old root is lost/compromised, disable acquisition/execution and perform out-of-band owner rebootstrap; an administrator must not silently designate themselves as owner. Preserve incident/history and invalidate old permits.
- Restored databases/registries start inactive. Reconcile an independently held current registry/revocation epoch and artifact tombstones before accepting any old permit. A rolled-back backup cannot resurrect rights. Reissue scoped authority only after the current owner verifies the restore; original signatures/history remain preserved.

## Evidence and privacy

Retain designation, owner enrollment decisions, fingerprint verification, possession outcomes, versioned registry changes, refusals, expiry/revocation and readback evidence in a protected audit store. Use pseudonymous principal IDs in public reports; public keys are not secrets but human identity/contact and registry topology need not be public. Keep image/model bodies, sealed chips, raw vectors and actual permits out of public Actions reports. Proposed asset retention is <=30 days from acquisition unless a new owner decision explicitly extends it; job temporaries are removed promptly, and independent tombstones control restore. These are review proposals, not currently provisioned retention/authority records.
