# Phase 1B identity boundary

Phase 1A was accepted after PR #1 and hosted validation of merged main `683180e`; see [acceptance](../phase1a/ACCEPTANCE.md). Phase 1B is authorized on `codex/phase-1b-identity-security`. Phase 1C is not authorized.

The Next BFF forwards only fixed identity paths to the loopback API. Browser tokens remain server-side. Keycloak authorization code flow uses S256 PKCE, state, nonce, a fixed redirect URI and a confidential client. Required password and OTP executions carry authentic AMR references with bounded lifetimes. Direct password grants, implicit flow, service accounts, self-registration, password recovery and remembered sessions are disabled in the synthetic realm. The API requires RS256, a known signing key, issuer, audience, client, expiration, issued-at, authentication time and both password/OTP claims. Each authenticated request also introspects the token with Keycloak. Missing IdP evidence denies access, including during outages. No JWT role claim grants application permissions.

Opaque random browser sessions have only SHA-256 identifiers in PostgreSQL. Fernet encrypts the token server-side with a separately supplied private runtime key; CSRF hashes are separate. Cookies are Secure, host-only, HttpOnly (session/flow), SameSite Lax; the separate CSRF token is readable by same-origin code and uses Strict. Mutations require an exact fixed Origin, same-origin Fetch Metadata when supplied, and the session-bound CSRF token. No local/session storage contains tokens. Sessions expire after the earliest token expiry/30-minute absolute deadline and 10-minute idle timeout. Logout revokes the local session immediately. There is no refresh-token retention: expired access requires fresh password+OTP authentication. A stolen still-valid bearer token remains bounded by IdP revocation/expiry; local logout is not asserted to revoke a separately stolen bearer token globally.

Every request resolves an explicitly provisioned, non-disabled OIDC principal; permissions come from live PostgreSQL memberships, organization approval and scoped case grants. Organization administrators see only their active organization memberships/audit metadata. The narrowly scoped membership function can grant/revoke reviewer or supervisor for another explicitly provisioned principal, at most 30 days. It cannot self-elevate or issue org_admin, safeguarding, authority or privacy roles. Initial organizational approval, sensitive roles and case grants require an explicit controlled bootstrap; this engineering phase does not approve an NGO or caller's legal authority. Administrators receive no case read grant automatically. Case-permission checks return the same 404 for absent and inaccessible IDs and do not return child data.

Runtime remains non-owner/NOBYPASSRLS. All 41 application tables retain FORCE RLS. A new FORCE-RLS platform session table is accessible only through fixed security-definer functions owned by the NOLOGIN policy role. Functions use fixed search paths, parameterized calls and explicit ACLs. SQL session context is a trusted application boundary; stolen arbitrary runtime SQL credentials are not contained by spoofable context settings. Migration credentials never enter the API.

Membership changes and case-permission outcomes append minimized per-organization SHA-256 chained audit records under transaction locks. A denied case probe commits its audit outcome; failed/denied changes roll back atomically. Login/logout append to currently active organizations. Ordinary runtime cannot update/delete audits or access session rows directly. Audit reads exclude tokens, bodies, contacts, custody and child identities. Chain integrity is tested in PostgreSQL. Independently administered write-once export/signing remains an operational release requirement; a local chain is not immutable against database administrators.

The local synthetic stack uses a two-day test CA, loopback TLS termination at `https://127.0.0.1:3443` (BFF) and `https://127.0.0.1:8443` (IdP). Internal API/IdP links remain on isolated development networks. The pinned TesterArmy engine exposes no per-context custom CA option; a disposable CI runner installs its ephemeral certificate in system/NSS trust. macOS local trust requires explicit owner approval and cleanup. No certificate-validation bypass or insecure-cookie mode exists. Keycloak `start-dev`/embedded storage and this loopback termination are engineering fixtures, not production deployment configuration.

The 32 reporting/media/biometric/safeguarding domain operations remain 503. No child intake, child DTO, media, model, disclosure, release or Phase 1C workflow is implemented. Existing legal/safeguarding/model research approvals and pending tests remain unchanged.

Membership writes require a UUID `Idempotency-Key`, scoped to principal and organization in a separate FORCE-RLS identity command ledger. Exact replay rechecks current administrator authority, returns the original outcome without a second mutation/audit event, and different-body reuse returns 409. The non-idempotent inner SQL routine is not executable by runtime. UUID identifiers and body hashes contain no child data; operational ledger retention/cleanup remains subject to the existing retention approval gate. The new wrapper and its transaction rollback are covered by direct PostgreSQL and real HTTP tests.
